# Security data handling

Updated: 2026-08-02

## Scope

This policy covers AI credentials and request history, secret-bearing network traffic, retained page data, diagnostics, exports, and tracing payloads. `tooling/configs/qa/security-storage-ownership.data.json` and `tooling/configs/qa/security-network-ownership.data.json` are the machine-readable owner inventories.

## AI provider secrets

- Provider metadata is separate from API secrets and may include only identifiers, display/configuration fields, timestamps, connection type, and `hasStoredApiKey`.
- Plaintext API keys and passphrases must never enter local, sync, or session storage, logs, UI responses, exports, diagnostics, or traces.
- Stored provider secrets use AES-GCM with per-secret IVs. Transparent mode keeps an extension-local key and is obfuscation against accidental inspection, not protection from a compromised browser profile or extension runtime.
- The approved storage owners are the exact `secretStorageOwners` entries in the storage ownership registry. The pre-v3 migration remains an explicit current-backend exception for converting legacy plaintext records and cleaning obsolete state.

### Optional passphrase protection

- Passphrase protection is opt-in. Enabling it decrypts transparent-mode envelopes, re-encrypts them with a passphrase-derived key, persists only non-secret protection metadata, removes `AI_LOCAL_SECRET_KEY_STORAGE_KEY`, and keeps the unlocked derived key only in background-runtime memory.
- Persistent `AI_SECRET_PROTECTION_KEY` metadata may contain mode, version, KDF parameters, salt, and an encrypted verifier, never raw key material.
- Passphrase-derived key material is in-memory only. It must not be written to local, sync, or session storage. `AI_PASSPHRASE_SESSION_KEY_STORAGE_KEY` is a legacy cleanup constant and never authorizes persistence.
- Transition markers are non-secret and must be written before durable enable, disable, or reset changes. Recovery removes stale markers, completes committed cleanup, or fails closed without simultaneous valid passphrase metadata and transparent key material.
- Unlock request metadata may use session storage only under `AI_SECRET_UNLOCK_REQUESTS_STORAGE_KEY` and may contain request identity, extension-page ownership, purpose, lifecycle status, timestamps, and terminal failure reason. It must not contain passphrases, derived keys, API keys, prompts, page payloads, cookies, authorization headers, or secret envelopes.
- The current KDF is PBKDF2-HMAC-SHA-256 with 600,000 iterations, a 16-byte salt, and a 256-bit AES-GCM key. Metadata is versioned for an explicit future KDF or trust-anchor migration.
- A local-storage dump must not decrypt passphrase-protected secrets. Weak passphrases, an active unlocked runtime, and a compromised extension remain residual risks.
- Forgotten passphrases are unrecoverable. Reset clears provider secrets and marks providers as missing stored keys.
- Provider-backed features unlock through the background-owned flow and extension settings page at `apps/extension/src/settings/index.html?aiUnlock=1&requestId=...`; content pages must not render passphrase overlays. Chrome built-in AI does not use this path.
- The unlock cache is fail-closed and disappears with MV3 worker memory. After worker eviction or restart, secrets remain locked until a new unlock succeeds; recovered completed requests report `restart-required` when their in-memory key is gone. See the [Chrome service-worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

## Sensitive retention

- Browser storage must not retain page-derived prompts, Markdown/JSON payloads, raw responses, HTML, cookies, or authorization values unless an explicit registry owner and policy exception exist.
- User-requested web snapshots may retain sanitized HTML/CSS, current non-credential form-control state, and either a full-page raster or an explicitly labeled visible-area fallback only as immutable local OPFS assets referenced by IndexedDB `web_snapshots` metadata and a linked media entry. The fallback uses the distinct `page-viewport-preview.png` package path, marks the Web-copy component partial, and is never published as `page-screenshot.png`. Recognized password, sign-in-code, and payment-control state is removed recursively from retained HTML and visually masked in the raster across light DOM and accessible open shadow roots. Scripts, handlers, unsafe URLs, browser storage, page IndexedDB, API bodies, and arbitrary live JavaScript state remain excluded. Other visible private pixels, including content drawn into images, canvas, video, or inaccessible closed shadow roots, can remain in the screenshot and are disclosed before capture; users must inspect the snapshot before sharing it.
- Design-review style edits are session-only and must not retain templates, restore rules, selector scopes, page text, images, or style assets. `sniptale_page_style_registry` remains listed only so local-data erasure also removes any stale alpha browser-storage record.
- Unsaved annotation template forks may be retained in browser session storage for the originating tab so visual work survives a reload. The retained snapshot is limited to text-free frame, comment, and numbering appearance settings: comment body, title and badge text, manual numbering values, and instance identities are excluded. Records are revisioned to reject stale document writes, removed when the tab closes, excluded from sync, export, and diagnostics, and covered by verified local-data erasure.
- Annotation template tags and the globally active tag filter are bounded user-authored preferences retained in sync storage. Tag labels and assignments remain catalog metadata: they are excluded from applied annotation snapshots, library backup, diagnostics, logs, and automatic exports; preference-preserving erasure retains them, while factory reset removes and verifies the canonical sync key.
- Saved Gallery views are bounded local preferences containing a user-authored name, one Gallery category, status and tag selections, and canonical facet value identifiers. They contain no media bytes or local asset identities, remain excluded from sync, diagnostics, logs, and selected-item packages, and are included only in an explicit full-library backup. Restore treats this manifest section as hostile input, validates exact fields and resource limits before mutation, applies the user-selected archive conflict policy, and never mutates assets when a view is deleted. Preference-preserving erasure retains the canonical local key, while factory reset removes it.
- LLM history is metadata-only: timestamp, model, request kind, counts, and status. Legacy prompt-bearing records are normalized away on read.
- Model egress uses the shared payload-bound lease, proof, normalization, redaction, and transport pipeline. Point-of-action UI discloses provider, model, prompt inclusion, page-data classes, and metadata-only retention before submit.
- Scenario pending-capture session state may hold metadata and a temporary asset reference; screenshot blobs stay in the scenario temp-asset store.
- Frame-annotation image export may stage one local-only base PNG, sanitized annotation snapshots (including committed callout text), and one derived PNG in the core IndexedDB `frame_annotation_raster_jobs` store. Each input and output is capped at 64 MiB, no more than three jobs are retained, and records expire after one hour. Payloads are excluded from backup, sync, automatic export, and diagnostics; consume, cancellation, lease expiry, offscreen startup recovery, and local-data erasure remove them. The background media exclusion is reserved before offscreen preparation and remains held for the live raster lease. After offscreen persistence bootstrap is ready, the client acquires the cross-context persistence transition gate, confirms that the background lease survived with the same identity, then stages the first payload and retains the gate through terminal cleanup. Privacy erasure reserves the media exclusion before the transition gate and canonical write barrier. Together they prevent startup lock inversion and stop a pre-erasure continuation from recreating payload after successful erasure, including across an MV3 worker restart.
- User-selected video-editor Cache mode may retain local-only derived AVC preview segments in the dedicated IndexedDB database `sniptale-video-preview-cache`. The cache is advisory, limited to 14 days, 12 records, and 512 MiB, excluded from project export, backup, sync, and diagnostics, removed before project deletion, and always removed and absence-verified by local-data erasure. Preview preferences follow `preservePreferences`; derived media never does.
- The beta database stores editable images, video projects, and scenarios as stable-ID aggregates. Immutable originals and owned dependencies remain authoritative beside a revisioned workspace; `aggregate_presentations` contains only replaceable previews and thumbnails and never owns lifecycle. Library backup includes library aggregate authority and its current or stale presentation, while draft retention advances only after a successful workspace mutation. Local-data erasure removes roots, workspaces, presentations, and dependencies.
- Active video recording streams MediaRecorder chunks directly into immutable objects under the extension origin private file system root `sniptale-assets`; IndexedDB retains only recording metadata, `AssetRef`, ownership, publication/physical-delete operations, media mirrors, and outbox state. Each object is protected first by a `writing` marker and a cross-context exclusive Web Lock, then by a durable `ready` journal until one IndexedDB transaction publishes the complete graph. Startup replays ready publications and removes a writing object only after an `ifAvailable` exclusive lock proves that no writer remains. Recording sessions keep a 64 MiB aggregate in-flight write ceiling and reserve 64 MiB quota headroom; OPFS write failures remain authoritative. Backup reads OPFS-backed files and restore writes OPFS objects before publishing metadata under an abortable durable operation. Asset bytes remain local-only except when a user explicitly downloads or exports them and are excluded from sync, diagnostics, and traces. Local-data erasure invalidates and aborts active writers, removes both `sniptale-assets` and legacy `sniptale-recording-staging`, and verifies absence under the persistent-data erasure barrier after media mutations have been excluded and the recording offscreen runtime has closed.
- Gallery media import is an explicit user-initiated local-file flow, separate from backup restore. It accepts only the bounded image and video MIME profile, applies the canonical per-media size limits, and requires browser image or video decoding before publication. Imported images use the image aggregate owner; imported videos use the immutable OPFS recording-asset owner with standalone video metadata. Files are committed independently so one rejected file does not discard successful imports; rejected filenames may be shown in the live Gallery result but are not persisted, logged, exported as diagnostics, or retained in traces. Imported bytes remain local-only, participate in ordinary Library backup and deletion, and are removed by canonical local-data erasure.
- Durable project media and imported scenario images use the same immutable OPFS object authority. Their IndexedDB domain rows contain opaque local asset IDs and byte metadata only; project or scenario aggregate transactions publish refs, owners, domain metadata, mirrors where applicable, and physical-delete intents atomically. Every ordinary durable writer holds the shared persistence-transition admission from its first OPFS marker through publication or discard, so verified local-data erasure cannot be followed by a pre-erasure continuation. Scenario pending-capture blobs, scenario export metadata and thumbnails remain on their existing bounded owners. Backup archives never expose local asset IDs: export hydrates referenced OPFS files and streams the ZIP into a temporary OPFS object retained until the browser reports the user-initiated download as complete or interrupted; persistent terminal cleanup failure is surfaced while the retained release authority remains retryable. Restore rejects duplicate media and durable owner identities before effects, streams archive entries into newly allocated objects, and commits them through the durable restore operation. Startup recovery replays committed publication intent and safely collects unreferenced objects, while the read-only cross-domain audit reports missing objects, refs, owners, and domain-owner mismatches without repairing authority.
- The first beta persistence generation uses IndexedDB `sniptale-db` version 1 plus exact per-domain version rows. Alpha `sniptale-video-db` versions 1–30 are not migration sources. Their one-time deletion and any explicit Gallery recovery reset are journaled before deletion, resume under the persistent-data barrier, remove associated OPFS/cache data, and verify absence before the beta database is admitted. The journals and future backup receipt contain fixed transition metadata only and are removed by local-data erasure. Supported beta upgrades preserve durable domains, preflight quota, and fail closed for corrupt, future, unsupported, or unbacked destructive formats.
- A finalized recording creates one exact `video-recording-completion-outbox` row in the existing IndexedDB `state_manager` store in the same transaction as its recording and media-library rows. The outbox contains recording IDs and an optional project ID, never media bytes, URLs, page data, or diagnostics. Offscreen restart replays this row before readiness, and exact background acceptance retires it. An unacknowledged post-record decision does not expire; only an acknowledged session-storage tombstone has a 12-hour retention bound. Local-data erasure clears and verifies the complete `state_manager` store together with committed media and prevents an active writer from recreating the row across the erasure barrier.
- Raw voice-input transcripts and recognition results are session-only. They may pass from the offscreen document through the background coordinator to the single owning explicitly authorized extension-page or content-runtime Port, but must not enter local, sync, or session storage, automatic exports, diagnostics, or traces. When a user keeps recognized text in a Design Review draft and explicitly commits that draft, the text loses voice provenance and becomes ordinary annotation content; a later, separately trusted user-activated annotation copy or download may include it. No recognition event may itself commit, persist, or export the draft. Language, recognition mode, and the selected microphone device identifier are persisted as ordinary sync preferences; the device identifier is never logged or rendered as a fallback label. Local recognition requests the fixed `dictation` quality when Chrome supports that option; browser-managed fallback uses Chrome's built-in service without extension-owned credentials or network transport.

## Network secret ownership

- Secret-bearing headers belong only to canonical transport owners. The approved AI owner is `apps/extension/src/background/ai/llm/transport/request.ts`.
- `fetch(..., { credentials: 'include' })` is authenticated page-context traffic and is allowed only for exact owners in the network registry. Owners must narrow page-derived URLs and reject cross-origin or suspicious targets.
- Web-snapshot credentialed asset fetches are same-origin only. User-enabled external assets use background-owned anonymous fetches with `credentials: 'omit'`, reject obvious private targets, follow redirects only under the popup policy described below, and fail as warnings. DNS rebinding remains a residual browser limitation because `fetch` does not expose the resolved IP.
- Page Web copy is an explicit point-of-action Package Contents choice. Its nested controls explain and govern authenticated same-origin and anonymous cross-origin asset loading. Anonymous external resources allow redirects by default and expose a nested popup control to disable them. Redirect requests omit credentials and the final URL must still be a public HTTPS target before response bytes are accepted. Chromium owns intermediate redirect traversal, so enabling this option lets a public asset endpoint direct an anonymous request through other addresses before Sniptale can validate the final URL. A separate default-off control may allow a user click in Viewer to open a validated HTTP(S) target in a new browser tab; archived links remain inert, page-authored capability attributes are discarded, and Viewer never navigates its sandboxed document. Opening a live target leaves the offline boundary and sends an ordinary request to that site.

## Settings transfer

- Settings transfer is an explicit user-initiated local JSON export/import for transferable persisted controls. It is separate from media-library and project backup and never reads projects, media, caches, permission grants, runtime status, or action state. Web-copy resource and external-link preferences are configured at the point of action and remain excluded from Settings transfer.
- Exported AI provider metadata may include provider identity, connection type, display name, and base URL. Provider credentials, the stored-credential presence flag, passphrases, encrypted envelopes, local or derived cryptographic material, KDF/protection metadata, and secret-transition state are excluded from the package, preview, report, diagnostics, and logs.
- Device identifiers, including the selected voice microphone, are excluded. Import explicitly restores the system-default microphone selection. Prompt text and private base URLs are included only after the user initiates export and the UI discloses those classes.
- Import treats the file as hostile input: it enforces a 2 MiB UTF-8 limit, depth 32, 50,000 JSON nodes, format and domain schema versions, per-domain parsing, dependency closure, and storage-quota preflight before a background-owned commit. The ordinary owned Settings page is the only authorized sender.
- Import reports use fixed outcome and reason fields and never include raw exceptions or secret values. Commit revalidates current state and compensates completed storage writes; an unverified rollback is surfaced as a blocking failure.

## Diagnostics

- Persisted, exported, logged, or traced diagnostics pass through `packages/platform/src/observability/diagnostics/sanitizer.ts`.
- Only exact `diagnosticSanitizerOwners` entries are tracer exceptions. Other collectors and sinks must import the canonical sanitizer and prove sanitization before every write.
- Page Package separates standard diagnostics from explicit extended page evidence. Standard diagnostics retain the existing heavily redacted Export Manager artifacts. Extended evidence is acquired from the caller-supplied live document before safe Web-copy preparation and is included only when the user selects Extended page data for Download or Library; it is never rendered as HTML. Its DOM projection is stored as `text/plain` under an `.html.txt` path; every retained scalar passes the canonical raw diagnostic sanitizer. Form-control state, cookies, browser storage, authorization headers, request/response bodies, script and inline-handler bodies, stylesheet bodies, `srcdoc`, file values, and arbitrary JavaScript state remain excluded. Script and stylesheet evidence is limited to sanitized metadata, bounded lengths, and injected hashes. Extended evidence can still contain visible private page text, ordinary attributes, and safe URL query values; its Package Contents row therefore describes the captured data at the point of selection without adding a separate warning banner. A Library package retains the selected evidence as local immutable package bytes and carries it through an explicit full-library backup.
- Page Package has no legacy Web Snapshot migration or cutover path. Current packages are validated directly at their archive boundary; old layouts are outside the supported import contract.
- Standalone Web Snapshot import is an explicit Library action, separate from backup restore and from capture enablement. It accepts only the current Page Package schema with the `save` intent and `standard` diagnostics profile, treats every archive as hostile, verifies its exact inventory and bounded streamed digests before preview, and repeats the same verification after confirmation. Imported HTML, CSS, SVG, local resource references, screenshot, and thumbnail are validated or re-sanitized; the package is rebuilt with new identifiers, sizes, and digests before the existing atomic Web Snapshot publication owner stores it. Imported scripts, handlers, forms, `srcdoc`, network loads, archive identities, permissions, cookies, storage, and runtime state never become Viewer or persistence authority. A failed import leaves no Library record or durable package object.
- Page Package transfer never retains aggregate archive bytes in the service-worker heap. The authorized content producer sends sequential base64 envelopes whose decoded body is capped at 512 KiB; background admission validates the exact active job, sender-resolved tab, ordinal, staged identity, sequence, finality, page count, per-chunk bytes, and aggregate page bytes before appending one chunk to the canonical OPFS asset writer. Before Export download or Library publication, the background reads the staged object as a `File`, parses the archive and manifest as hostile input, verifies the exact inventory, sizes, paths, MIME profile, intent binding, and every entry SHA-256 through an abortable incremental stream. `@noble/hashes` is an exact-pinned production dependency because its incremental SHA-256 state permits this hostile-archive validation with bounded memory; replacing it requires equivalent streaming and abortability proof. A finalized staged object remains disposable and non-durable: Library publication writes separate immutable package and screenshot objects, while success, failure, cancellation, privacy erasure, or owner-scoped release discards job staging. An MV3 restart loses in-memory staging authority and canonical writing-marker recovery collects inaccessible partial objects; durable finalized refs are reconciled by the Page Package job record.
- Recording diagnostics UI discloses action/error/meta diagnostics, service logs, IndexedDB retention, and JSON/ZIP export behavior before enablement or download.
- Preview-cache diagnostics contain fixed reason codes, counts, durations, byte totals, and phase names only. They exclude project IDs, digests, fingerprints, source URLs, blobs, frame content, document source, and asset bytes.
- Voice-input diagnostics contain request/session identifiers, language, requested and effective mode, API flavor, fixed quality, normalized availability and error/fallback codes, phase, duration, sequence, character count, confidence, and a bounded normalized microphone level only. The offscreen document derives that scalar level at 10 Hz for the owning live Port and retains no history; the Settings consumer builds its short waveform in memory. Device identifiers, transcript text, PCM/audio, raw recognition results, and raw exception messages are excluded; the runtime message tracer replaces transcript text with character count before generic sanitization.

## Deterministic guardrails

`verify-secret-storage`, `verify-sensitive-retention`, `verify-fetch-ownership`, and `verify-diagnostic-sanitization` enforce these registry-driven rules. A new owner requires the registry and this policy to change together.
